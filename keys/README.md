# Herd repository signing key

This directory holds **only the public key** that signs the CapivaraOS Herd
update repository. Trust in updates **does not depend on the host** serving the
files: `gpgcheck` + `repo_gpgcheck` reject any package or metadata not signed by
this key, even if the server is compromised.

## Files

| File | Commit? | What it is |
|---|---|---|
| `gen-signing-key.sh` | yes | Ceremony (offline) that generates the key pair. |
| `RPM-GPG-KEY-capivaraos-herd` | **yes** | **Public** key (ASCII). Shipped by the `capivaraos-herd-repos` package. Generated by the script. |
| **private** key | **NEVER** | Kept offline. Never in this repository or on the repository server. |

## Trust model (why it is safe)

- The **private** key signs every RPM (`rpm --addsign`) and the repository
  `repomd.xml` (detached signature `repomd.xml.asc`).
- The **public** key ships in the `capivaraos-herd-repos` package, is installed at
  `/etc/pki/rpm-gpg/RPM-GPG-KEY-capivaraos-herd` and imported into the rpm keyring.
- On the client, `gpgcheck=1` verifies the signature of each package and
  `repo_gpgcheck=1` verifies the signature of the repository index. A forged or
  tampered update is rejected.
- That is why the **file host does not matter** for integrity.

## First generation (once, OFFLINE)

```bash
./keys/gen-signing-key.sh
```

The script generates an RSA 4096 key, exports the **public** key to
`keys/RPM-GPG-KEY-capivaraos-herd` (commit this file) and the **private** key to
a file in your `$HOME`, which you must **store offline and delete with
`shred`**. Publish the **fingerprint** on the Security page of the site/docs so
users can verify it.

## Signing at publication

On the machine that publishes the repository (see `publish-repo.sh`):

```bash
# import the private key only when signing
gpg --import /caminho/seguro/privada.asc
# tell rpm which key to use
cat >> ~/.rpmmacros <<'EOF'
%_gpg_name CapivaraOS Herd (repo signing key)
%_gpg_digest_algo sha512
EOF
```

## Rotation / compromise

- **Planned rotation:** generate a new key, sign with **both** (new + old) for a
  period, ship the new public key in an update of `capivaraos-herd-repos`, and
  only then retire the old one.
- **Compromise:** revoke (publish the revocation certificate), generate a new
  key, push an update of `capivaraos-herd-repos` with the new public key and
  announce it on the Security page. This is why the revocation certificate must
  also be generated and kept offline.

> This key is used for **repository/RPM** signing (RSA) and nothing else.
> Any other project key has a different purpose and chain; do not use one in
> place of the other.
